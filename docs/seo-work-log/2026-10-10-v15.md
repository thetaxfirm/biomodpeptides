## Evidence and change

A source audit found Account only toasted a failed account read and then displayed Loading account details indefinitely. It also ignored an initial storefront-state failure. Checkout directs customers with uncertain payment outcomes to order history, making this a real support and purchase-recovery barrier. Account now shows persistent read errors and retry controls, guards repeated retry clicks, rejects stale owner/read/unmount responses, and keeps previously loaded information when a refresh fails. A newer read after an existing successful account action supersedes an older pending retry. Recovery reads do not create orders, resume checkout or charge a payment. Existing mutation semantics, Cart, Checkout and PaymentReturn remain unchanged. Guest wishlist access is preserved after initial state loads; failed initial loads no longer look like an empty wishlist.

The live privacy page also retained prelaunch draft language and described account/cookie storage incompletely. A source audit and production configuration readback confirmed Supabase authentication, Cloudflare D1, and the default Authorize.net integration. The corrected notice identifies server-stored carts behind a cookie identifier, storefront account records, hosted card entry, operational security IP records, and the separate aggregate-reporting retention boundary. It adds an update date and a route for access/correction/deletion requests. It does not promise automatic business-record deletion, a retention deadline or legal compliance. Optional service vendors are not asserted as live by name. No data flow or retention behavior is changed by the notice. The terms-of-sale draft wording remains a separate review item.
